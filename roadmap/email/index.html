Email

Send email to the people in the Contacts store, split by store status and role. Planned 2026-10-09 with Henry. Built on the contacts-upstream line so it can go upstream after contacts does.

The one-paragraph version. PartnerDex already holds a few hundred merchant contacts (Mantle import + live iziGift capture), each linked to a store, a role, and that store's subscription state. There is no way to message them. This feature works the way Mantle did: apps identify each store to PartnerDex (contacts + custom attributes), Henry saves audiences on the Contacts page, writes an email with merge fields and page buttons, and PartnerDex sends it through Resend with a preference page per email type, a postal footer, and per-recipient history. Apps can also send data for one store and let PartnerDex fill a template (the weekly recap first). Scheduled emails, richer styling, and flows come after.

The problem today

  • The list exists; the send does not. contacts / contact_shops / contact_suppressions (migration 4, src/db/migrate.ts) hold the people. The Contacts page (src/contacts/list.ts, web/src/components/Contacts.tsx) can search and suppress them. Nothing in src/ sends an email — no Resend client, no transport, no template, no unsubscribe route.
  • No way to split by what matters. The Contacts filters are data-hygiene filters (ContactLinkedFilter = 'all' | 'unlinked' | 'ambiguous' | 'suppressed'). The question Henry needs answered — "every owner and staff member of a paying iziGift store" — needs the per-store status that only src/customers/index.ts computes (statusOf() → 'paying' | 'trialing' | 'installed' | 'churned' | 'gone'), and it is private to the Customers list today.
  • The suppression store has no inbound path from email. suppressContact() accepts 'resend_webhook' | 'manual' | 'csv_import', but no route produces resend_webhook, and an unsubscribe link has nowhere to land.
  • The reason it matters now. ~158 paying iziGift stores, fewer than 50 active (Henry, 2026-10-01). The merchant newsletter has been parked since July for want of a send tool. A broadcast to "paying but not using it" is the cheapest churn defense available.

The send, end to end

Contacts page, an audience tab ── definition {appId, statuses, roles} ──► resolveAudience() ──► count + rows (live)
      │
Campaigns tab ── subject + body (+ {{first_name}} {{shop_name}}) ──► Test send to one address
      │
  Prepare  ──► recipients frozen into email_sends (status=queued), suppressed re-checked
      │
  Confirm  ──► Henry types the frozen count ──► status=sending
      │
  Runner   ──► 100 at a time → Resend /emails/batch (Idempotency-Key per batch) → status=sent + resend_id
      │
  Recipient ── List-Unsubscribe one-click / footer link ──► /p/:token ──► email_preferences (this type off; 'all' = every marketing type)
      │
  Resend webhook (S4) ──► delivered / opened / clicked stamps; bounced(hard) + complained ──► suppressContact(source='resend_webhook')

Why each sprint ships alone

S1. One migration that only creates audiences, one read-mostly router, and saved lists on the Contacts page whose All contacts tab keeps today's behaviour. Henry can count and export any audience into any tool.

S2. New tables and a new public route behind the existing ingest token. The old contacts ingest is unchanged, so the deployed iziGift job keeps working until its own change ships. Value alone: store settings and time zones on the customer page.

S3. New tables, routes, a runner, and the Email page. With RESEND_API_KEY, PUBLIC_BASE_URL, or EMAIL_LINK_SECRET unset, Test and Send are disabled with a reason and the runner never starts. Resend refuses its own bounced and complained addresses, so sending before S4 is safe.

S4. A public webhook plus reads. With RESEND_WEBHOOK_SECRET unset the route answers 503 and campaigns show "sent" without detail.

S5. Templates start as Draft and the intake refuses Draft templates, so the deploy sends nothing until Henry sets one Live and iziGift starts calling.

Branching and upstream

Henry, 2026-10-09: "For now it will just be in my fork but eventually I will likely upstream it. We should build this as a branch off of contacts upstream."
  1. Create email-upstream from origin/contacts-upstream (= upstream main + the single contacts commit). Each sprint is a branch off email-upstream and merges back into it.
  2. To run it in production, cherry-pick each sprint's commits from email-upstream onto the fork's main (as done for S1) and fly deploy. Never merge fork main back into email-upstream — that drags CLAUDE.md, roadmap/, and fork-only commits into the future upstream diff (fork CLAUDE.md branching rule).
  3. Upstream PR opens only after the contacts PR merges upstream; rebase email-upstream onto the new upstream/main then.
  4. Keep it upstream-shaped: nothing iziGift-specific in code (no "iziGift" strings, no Henry defaults); sender identity lives in the UI-entered email_settings row; Resend sits behind a small EmailTransport interface so another provider can be added upstream without touching the runner.
