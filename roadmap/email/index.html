Email

Send email to the people in the Contacts store, split by store status and role. Planned 2026-10-09 with Henry. Built on the contacts-upstream line so it can go upstream after contacts does.

The one-paragraph version. PartnerDex already holds a few hundred merchant contacts (Mantle import + live iziGift capture), each linked to a store, a role, and that store's subscription state. There is no way to message them. This feature adds an Email section: build an audience (one app × store statuses × roles), write a plain-text founder email, send yourself a test, confirm by typing the recipient count, and PartnerDex sends it through Resend with a working unsubscribe link, a postal footer, and per-recipient history. Automated lifecycle email is v2/v3 and only scoped as open questions here.

The problem today

  • The list exists; the send does not. contacts / contact_shops / contact_suppressions (migration 3, src/db/migrate.ts) hold the people. The Contacts page (src/contacts/list.ts, web/src/components/Contacts.tsx) can search and suppress them. Nothing in src/ sends an email — no Resend client, no transport, no template, no unsubscribe route.
  • No way to split by what matters. The Contacts filters are data-hygiene filters (ContactLinkedFilter = 'all' | 'unlinked' | 'ambiguous' | 'suppressed'). The question Henry needs answered — "every owner and staff member of a paying iziGift store" — needs the per-store status that only src/customers/index.ts computes (statusOf() → 'paying' | 'trialing' | 'installed' | 'churned' | 'gone'), and it is private to the Customers list today.
  • The suppression store has no inbound path from email. suppressContact() accepts 'resend_webhook' | 'manual' | 'csv_import', but no route produces resend_webhook, and an unsubscribe link has nowhere to land.
  • The reason it matters now. ~158 paying iziGift stores, fewer than 50 active (Henry, 2026-10-01). The merchant newsletter has been parked since July for want of a send tool. A broadcast to "paying but not using it" is the cheapest churn defense available.

Why each sprint ships alone

S1 alone. One migration that only creates email_audiences, one read-mostly router behind the dashboard gate, one new page. No existing query changes behaviour: shopStatuses() is extracted from the code the Customers list already runs, and the Customers list keeps calling the same SQL (its tests prove it). Value on its own: Henry can answer "who exactly is a paying iziGift owner or staff member?" with a count and a list, and export the CSV into any tool he already has — the newsletter is unblocked even if S2 slips.

S2 alone (after S1). Adds tables and routes; touches no existing write path except widening the suppressContact() source union by one value. With RESEND_API_KEY unset the Send and Test buttons are disabled with a reason and the runner never starts — the app behaves exactly as after S1. Resend already refuses to deliver to addresses on its own bounce/complaint suppression list, so sending before S3 does not hammer bad addresses; S3 only mirrors those events into PartnerDex so the Contacts page and future audiences see them.

S3 alone (after S2). A new public webhook route plus reads. With RESEND_WEBHOOK_SECRET unset the route answers 503 and campaigns simply show "sent" without delivery detail — S2 is unchanged.

Branching and upstream

Henry, 2026-10-09: "For now it will just be in my fork but eventually I will likely upstream it. We should build this as a branch off of contacts upstream."
  1. Create email-upstream from origin/contacts-upstream (= upstream main + the single contacts commit). Each sprint is a branch off email-upstream and merges back into it.
  2. To run it in production, merge email-upstream into the fork's main and fly deploy. Never merge fork main back into email-upstream — that drags CLAUDE.md, roadmap/, and fork-only commits into the future upstream diff (fork CLAUDE.md branching rule).
  3. Upstream PR opens only after the contacts PR merges upstream; rebase email-upstream onto the new upstream/main then.
  4. Keep it upstream-shaped: nothing iziGift-specific in code (no "iziGift" strings, no Henry defaults); sender identity lives in the UI-entered email_settings row; Resend sits behind a small EmailTransport interface so another provider can be added upstream without touching the runner.

Deliberately out of scope (v1)

  • Lifecycle / automated / triggered email (→ S4, v2/v3).
  • Splits beyond store status + role: MRR range, plan, install date, login recency, usage metrics, tags, hand-picked lists.
  • HTML templates, images, a WYSIWYG editor, A/B subjects.
  • Multi-app audiences in one send (one app per audience; status is per app).
  • Unlinked contacts — never eligible.
  • Reply handling inside PartnerDex — replies go to the Reply-To inbox.
  • Scheduled sends (Q5).
  • Sending from iziGift. iziGift stays a contact producer; it gets no email code from this.
