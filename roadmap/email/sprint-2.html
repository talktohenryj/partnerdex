Sprint 2 — Compose + send

Not started · repo: partnerdex · branch email/s2-send off email-upstream · migration 5

Why this ships now

S1 answers "who". This sprint answers "send them this": a plain-text founder email, a test to yourself, a frozen recipient list, a type-the-count confirmation, and a resumable send through Resend with the two things the law and the inbox providers require — a working one-click unsubscribe and a postal footer. Today PartnerDex has no transport, no unsubscribe route, and no record of what was sent to whom.

Why this is independently deployable

New tables (migration 5), new routes, a new background loop, two new tabs. The only edit to existing behaviour is one more value in the suppressContact() source union. With RESEND_API_KEY, PUBLIC_BASE_URL, or EMAIL_LINK_SECRET unset — or with no DASHBOARD_PASSWORD — Test, Prepare, and Send return 403 with the reason, the runner does not start, and the app behaves exactly as after S1. Resend itself refuses addresses on its bounce/complaint suppression list, so sending before S3 is safe; S3 only mirrors those events back.

  8. Prepare / confirm / send / cancel — src/email/campaigns.ts
    • prepareCampaign(id): requires sendingBlockedReason() === null and domainStatus === 'verified', status draft|ready, subject and body present. Runs resolveAudience() (S1); in one transaction deletes old queued rows, inserts one email_sends row per recipient (merge JSON includes app_name from apps.name), snapshots sender settings onto the campaign, sets status='ready', recipient_count, prepared_at. Returns { count, excluded, sample[≤10], missingFirstName }. 0 recipients → 422.
    • startSend(id, confirmCount): status must be ready; confirmCount === recipient_count else 409 "Type {n} to confirm."; prepared_at within 60 min else 409 "The list is over an hour old. Prepare it again." Sets sending, started_at, wakes the runner.

    • sendTest(id, to?): renders with the first prepared or resolved recipient's merge values (falls back to placeholders), subject prefixed [Test] , test unsubscribe token, transport.sendOne(). to defaults to settings reply_to. Max 20 tests per campaign per hour (in-memory counter).

  9. Runner — src/email/runner.ts (new) Same shape as src/sync/scheduler.ts: a chained setTimeout, never two ticks at once, startEmailRunner() called from src/server/index.ts next to startSyncScheduler(), and only when sendingBlockedReason() is null. wakeEmailRunner() schedules an immediate tick. Tick (in-process, not the sync worker — it is I/O-bound):
    1. Pick the oldest campaign with status='sending'. None → sleep 30 s.
    2. Resume first: if rows with status='sending' exist (a crash or deploy mid-batch), resend exactly those rows with their stored batch_key. Resend's idempotency key returns the original result instead of sending twice (keys live 24 h; a batch stuck past 23 h → rows failed, error "idempotency window passed — check Resend before resending").
    3. Else take the next 100 queued rows by email. Re-check suppression now (someone may have unsubscribed from an earlier campaign mid-send) → those rows skipped/suppressed. In one transaction: batch_seq += 1, batch_key = campaignId + ':' + batch_seq, rows → sending.
    4. Render each row with renderEmail() from the campaign snapshot and its merge; call transport.sendBatch().
    5. Success → rows sent, resend_id, sent_at; bump counters. Non-retryable error → rows failed with the message. Retryable → leave sending, back off 5 s → 10 s → … → 5 min.
    6. No queued or sending rows left → campaign sent (or failed if every row failed), finished_at. Next tick in 1 s while a campaign is sending (well under Resend's default rate limit).
    Log one line per batch (campaign, batch, sent, failed) — never the recipient addresses.
