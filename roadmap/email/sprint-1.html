Sprint 1 — Audiences

Not started · repo: partnerdex · branch off email-upstream · migration 5 (see Q1)

Why this ships now

The split is the hard, valuable half. Today the only filters on people are hygiene filters (ContactLinkedFilter in src/contacts/list.ts), and the store status that decides who should hear what lives privately inside src/customers/index.ts (statusOf()). This sprint joins the two on the Contacts page itself: next to "All contacts", Henry saves audiences — pick an app, the store statuses, and the roles, and see exactly who that is, with suppression, unlinked, and ambiguous people moved to "left out" and each person counted once. An audience is a collection of contacts, so it lives where the contacts live, in the same table with the same columns. The Email page arrives with the first send (S2).

Why this is independently deployable

One migration (5) that only creates a table, one router behind requireAuth, and a reworked Contacts page whose All contacts tab keeps today's list, search, Show filter, sorting, paging, Suppress and Resolve. The edits to existing code: extract the per-shop status query in src/customers/index.ts into an exported helper that the Customers list keeps using unchanged; export sortShops from src/contacts/list.ts; add a status field to each store on GET /api/contacts (additive — old callers ignore it). If S2 never ships, Henry still gets counted, deduped, suppression-clean audiences he can export as CSV and paste into any sender.

  6. Audience model + resolver — src/audiences/audience.ts (new) 
    export const STATUSES = ['paying','trialing','installed','churned','gone'] as const;
export interface AudienceDefinition { appId: string; statuses: CustomerStatus[]; roles: ContactRole[] }
export interface Recipient { email: string; firstName: string|null; lastName: string|null;
  source: string; createdAt: string|null; lastSeenAt: string|null;   // same columns as All contacts
  isSuppressed: boolean; matchMethod: MatchMethod;
  shopId: string; shopName: string|null; shopDomain: string|null; role: ContactRole; status: CustomerStatus;
  otherShops: number }                                               // the "+N" on the Customers cell
export type ExclusionReason = 'suppressed' | 'ambiguous' | 'noStatus';
export interface ExcludedPerson extends Recipient { reason: ExclusionReason }
export interface AudienceResult { recipients: Recipient[];
  excludedPeople: ExcludedPerson[];          // one per person, sorted like recipients
  excluded: { suppressed: number; ambiguous: number; noStatus: number; merged: number };
  stores: number;                            // distinct shopId among recipients
  byStatus: Record<CustomerStatus, number>; byRole: Record<ContactRole, number> }
export function validateDefinition(input: unknown, db?: Db): AudienceDefinition   // throws AudienceError(…, 422)
export function resolveAudience(def: AudienceDefinition, db = getDb()): AudienceResult
export function optionCounts(def: AudienceDefinition, db = getDb()):
  { statuses: Record<CustomerStatus, number>; roles: Record<ContactRole, number> }
    validateDefinition: appId normalized with normalizeAppId() and checked with assertAppInScope(); statuses and roles non-empty subsets of the allowed values, deduped. AudienceError mirrors ContactsError (message + status) in src/audiences/errors.ts.
    resolveAudience, in this order:
    1. Load candidate memberships: SELECT cs.email, cs.shop_id, cs.role, cs.match_method, c.first_name, c.last_name, c.source, c.created_at, c.last_seen_at, c.is_suppressed, (sup.email IS NOT NULL) AS hard_suppressed FROM contact_shops cs JOIN contacts c ON c.email = cs.email LEFT JOIN contact_suppressions sup ON sup.email = cs.email WHERE cs.app_id = @appId AND cs.role IN (…roles). Unlinked people have no row here, so they are out by construction.
    2. Join each row to shopStatuses(db, appId). No entry → count in noStatus, drop. Status not in statuses → drop silently (not "excluded", just not asked for).
    3. match_method = 'ambiguous' → count in ambiguous, drop (Q3).
    4. is_suppressed = 1 or a contact_suppressions row → count in suppressed, drop. Both checks, because the mirror can lag a hand-edited row.
    5. Group survivors by email; keep the first by sortShops order (owner, then MRR); each extra row adds 1 to merged and 1 to that recipient's otherShops.
    6. Sort recipients by shop name, then email. Fill byStatus / byRole from the kept rows, and stores from their distinct shopIds.
    7. Build excludedPeople: every email that had at least one dropped row in steps 2–4 and no surviving row. One entry per person, taken from their first dropped row in sortShops order, with reason = the step that dropped that row. A person who is dropped on one store but kept on another is a recipient, not excluded. Sort like recipients.
    Counting is per person: excluded.suppressed / ambiguous / noStatus are the counts of excludedPeople by reason, so the summary link "14 left out" equals excludedPeople.length and the three parts add up to it.
    optionCounts gives the number beside each option in the Store status and Role menus: statuses[s] = recipients.length of resolveAudience({ ...def, statuses: [s] }) for each of the five statuses (current roles), and roles[r] likewise for each role (current statuses). These are after exclusions, so the checked boxes add up to the headline when nobody is on two stores. A few hundred contacts make the eight extra resolves cheap; do not cache.

Design mockup — Contacts with saved lists (chosen 2026-11-03)

One Contacts page. It opens on All contacts; filters narrow the list in place, and Save audience… turns them into a new tab. Saved lists are tabs above the table; the rules are filter buttons in one row above the table, so the table keeps the full width. An audience uses the same columns as All contacts. Drawn with the dashboard's own styles: the rules are copied from web/src/styles.css (Lumina Modern), cut down to the ones these screens use. The rail, masthead, tab strip, inputs, table, pager, and pills are existing components. Only the cv-, aud-, and check- classes are new, and they use the existing tokens only. The font falls back to the system font here; the app loads Inter.

Placeholder names and illustrative numbers — not real data. Links and controls do nothing. Each sample shows a few rows; the page shows 50.

What the mockup pins down

  • No rail change in S1. Contacts stays under Customers.
  • List tabs: the customer page's .page-tabs with .page-tab-count. The strip holds All contacts and the saved audiences only.
  • Rule buttons: 999px pill, 13px; the label in --muted, the value in 600 weight; dashed --border when unset, brand at 10% fill and 45% border when set. The menu is a 260px --surface-1 panel with --shadow-md, a small uppercase heading, and one row per value: checkbox, pill, count.
  • Actions sit at the right end of the rule row: Export CSV as a bordered button, Save audience… / Save changes as button.primary, the ⋯ menu as a bordered square button.
  • Summary line is inside the card, above the table: the count at 20px, the rest at 14px; "14 left out" is a link.
  • Table: fixed layout so the main list and Left out line up — 24 / 11 / 11 / 11 / 23 / 10 / 10%.
