Sprint 2 — iziGift producer (dual-write + backfill)

Not started · repo: iziGift-shopify · app code → feature branch + PR (not master)

Why this ships now

S1 gives PartnerDex a door. Nothing walks through it until iziGift sends events. iziGift already builds the exact payload Henry wants — TrackMantleOrderEvent::handle() computes USD order total, upsell revenue, gift card and store credit dollars redeemed — and sends it only to Mantle, where the customer page now shows "not authorized" for every metric.

Why this is independently deployable

It is a second, separate job. TrackMantleOrderEvent is not edited in its sending behavior; Mantle keeps getting the same event. The new job uses dispatchIfConfigured, so with the two env vars unset in production nothing is queued. A PartnerDex outage only fails a background job with backoff — never the order flow.

Build

  1. Extract the payload — app/Services/UsageOrderEventPayload.php (new) Move the property-building block from TrackMantleOrderEvent::handle() (the convertToUSD calls, the OrderRedemption lookup by user_id + shopify_order_id, the number_format array) into build(User $shop, $order): array. TrackMantleOrderEvent calls it; its Mantle request body stays byte-identical. Pin that with a test before moving the code.
  2. Config — config/services.php Extend the existing partnerdex block (line 88): 'usage_ingest_url' => env('PARTNERDEX_USAGE_INGEST_URL'), 'usage_ingest_token' => env('PARTNERDEX_USAGE_INGEST_TOKEN'). Reuse app_id. Add both to .env.example.
  3. Job — app/Jobs/SyncUsageEventToPartnerDexJob.php (new) Copy the shape of SyncContactToPartnerDexJob: $queue = 'background', $tries = 5, $backoff = [60,120,300,600], isConfigured(), dispatchIfConfigured(array $payloadOrBatch), Http::withToken()->timeout(10)->post(). Body: 
    { appId, eventName: "order", eventId: (string) $order->id,
  myshopifyDomain: $shop->name, occurredAt: order processed_at (ISO),
  properties: UsageOrderEventPayload::build($shop, $order) }
    Accepts a batch ({events:[…]}) for the backfill. 4xx other than 429 → log and stop (no retry); 5xx/429/timeouts → release with backoff.
  4. Dispatch — app/Jobs/OrdersPaidJob.php Next to TrackMantleOrderEvent::dispatch(...) at line 120, add SyncUsageEventToPartnerDexJob::dispatchIfConfigured(...) with the same $shop and $order. Same ->delay(now()->addSeconds(5)) the Mantle dispatch uses, so the OrderRedemption row exists when the payload is built.
  5. Backfill — app/Console/Commands/PartnerDexBackfillUsage.php (new) Limit: iziGift stores no orders table. The only order history it keeps is order_redemptions (orders that used a gift card or store credit). So a backfill from the DB covers redemption orders only — the same set BackfillMantleRedemptionEventsJob covered. Total Orders / Total Revenue for non-redemption orders start at go-live (open question Q5). partnerdex:backfill-usage {--days=365} {--shop=} {--batch=200} {--dry-run}. Query OrderRedemption::where('user_id', …) the way BackfillMantleRedemptionEventsJob.php:49 does. Event id = (string) $redemption->shopify_order_id — the same id the live job sends (BackfillMantleRedemptionEventsJob.php:78), so a later live event or a re-run overwrites and never duplicates. Skip shops with potentially_closed_at set. Dispatch one SyncUsageEventToPartnerDexJob per batch of 200. --dry-run prints counts per shop only.
  6. Deploy notes — In PartnerDex set USAGE_INGEST_TOKEN (Fly secret). In Forge set PARTNERDEX_USAGE_INGEST_URL=https://<partnerdex host>/api/usage/ingest and the token. Run the backfill with --dry-run, then for one shop, then all.
