Usage Metrics

Mantle-style usage events and per-customer usage metrics, inside PartnerDex. Fork-only for now. Planned 2026-10-02.

An app pushes usage events (for iziGift: one order event per paid order, with usdOrderTotal, usdUpsellRevenue, …). PartnerDex stores them raw. Henry then defines usage metrics in the dashboard — "Total Revenue = sum of usdOrderTotal on order" — and every customer page shows those metrics over a chosen window. Same model as Mantle, but the data lives next to MRR, churn and contacts in one SQLite file.

The problem today

  • Mantle holds the usage data, PartnerDex does not. iziGift sends one order usage event per paid order from app/Jobs/TrackMantleOrderEvent.php (dispatched in OrdersPaidJob.php:120) via APIService::trackMantleUsageEvent(). Nothing sends it anywhere else.
  • Mantle's customer page shows "Something went wrong — You are not authorized to access this metric" on every usage metric (Total Orders, Total Revenue, GC Dollars Redeemed, Upsell Revenue, Store Credit Dollars Redeemed). The data that made the page useful is not reachable today.
  • PartnerDex has no usage rail. It knows Partner API money (MRR, charges) and contacts. It has no table for app-side events, no ingest route for them, and no metric definition layer. CustomerDetail (src/customers/index.ts:306) has no usage field.
  • SQL works but is slow to use. Henry can answer "how much upsell revenue did shop X make last 30 days" with SQL on the iziGift DB. The point of this feature is a click, not a query.

Why each sprint ships alone

S1 alone. It adds one table through a new migration and one new route. No existing code reads the table, so nothing that works today can break. On its own it starts the history clock: every event a producer sends from day one is kept, and the raw events page lets Henry see them. Usage data cannot be recovered later the way Partner API data can, so starting capture early is the value.

S2 alone (after S1). It is a dual-write. The Mantle job stays exactly as it is. If PartnerDex is down or unconfigured, dispatchIfConfigured does nothing and the Mantle path is unaffected. The backfill puts past redemption orders into PartnerDex so S3/S4 open with some history (see Q5 — iziGift keeps no full orders table).

S3 alone. Definitions plus a preview over the raw events. Henry can define "Total Revenue" and see the aggregate for any customer from the settings page before the customer page knows about it.

S4. Pure read path over S1 + S3 tables. If no metric is flagged show_on_customer, the card does not render — the customer page looks the same as today.

Design decisions (taken)

  • Compute at read time, no rollup table. Same reason as src/customers/index.ts: one shop's events over a window are a few thousand rows; SQLite with an index on (app_id, shop_id, event_name, occurred_at) answers in milliseconds, and a rollup could silently disagree.
  • Re-sending the same event_id overwrites. Mantle does this and iziGift depends on it (TestMantleOverwrite, ZeroMantleBackfillEventsJob). Upsert on (app_id, event_name, event_id).
  • Properties are stored as JSON, summed with json_extract. iziGift sends numbers as strings ("13.03"), so the sum uses CAST(json_extract(properties, '$.' || property) AS REAL).
  • Store the domain as well as the resolved shop. An event can arrive before the Partner API sync knows the shop. Keep shop_domain; re-resolve rows with an empty shop_id after each sync.
  • Durable (Role 4). Usage events cannot be re-synced from anywhere. Migrations, not SCHEMA_SQL, and not wiped by rebuild.
  • Separate token. USAGE_INGEST_TOKEN, not CONTACTS_INGEST_TOKEN, so one leaked producer secret does not open both doors.

Deliberately out of scope

  • Billing on usage (Mantle usage-based charges). PartnerDex reads money from the Partner API; it does not bill.
  • Funnel events / "App events" (Mantle's other two event types). The ingest shape allows them later; no UI for them here.
  • Currency conversion in PartnerDex. The producer sends USD figures (usd*) and originals; PartnerDex sums what it gets.
  • A public SDK. iziGift's PHP job is the only producer.
  • Per-property filters in the UI (Mantle's "Filter by properties"). Column exists in S3; UI is S5 or later.
